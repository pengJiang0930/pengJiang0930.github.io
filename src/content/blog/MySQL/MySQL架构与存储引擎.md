# 数据库三范式

- 第一范式 原子性：字段具有原子性，不可再分（字段单一职责）
- 第二范式 唯一性：满足第一范式，每行应该被唯一区分，加一列存放每行的唯一标识符，称为主键（都要依赖主键）
- 第三范式 独立性：满足一二范式，且一个表不能包含其他表已存在的非主键信息（非主键值不依赖于另一个非主键值）

**范式优点与缺点：**

优点：范式化，重复冗余数据少，更新快，修改少，查询时更少的distinct

缺点：因为一个表不存在冗余重复数据，**查询可能造成很多关联**，效率变低，可能使一些**索引策略无效**，范式化将列存在不同表中，这些列若在同一个表中可以是一个索引。

2. 为什么优化器是核心？→ 同样SQL，执行计划差100倍性能，优化器决定"怎么走"
3. 为什么存储引擎可插拔？→ 业务场景多样：OLTP用InnoDB，OLAP用ColumnStore，临时表用Memory
4. MySQL 8.0为什么废弃查询缓存（Query Cache）？

   2. 高并发下缓存锁竞争严重，反而成为瓶颈；
   3. 应用层缓存（Redis）更灵活可控。
   4. 结论：专业的事交给专业的层。

## 连接器

1. 第一步， 你会先连接到这个数据库上， 这时候接待你的就是连接器。 **连接器负责跟客户端建立连接、 获取权限、 维持和管理连接**。 连接命令一般是这么写的： `mysql -h$ip -P$port -u$user -p`
2. 完成经典的TCP握手后， 连接器就要开始认证你的身份， 这个时候用的就是你输入的用户名和密码。 
   1. **如果用户名或密码不对**， 你就会收到一个"Access denied for user"的错误， 然后客户端程序**结束执行。**
   2. 如果用户名密码**认证通过，** 连接器会到权限表里面**查出你拥有的权限**。 之后， 这个连接里面的权限判断逻辑， 都将依赖于此时读到的权限。
   3. 这就意味着， 一个用户成功建立连接后， 即使你用管理员账号对这个用户的权限做了修改， 也不会影响已经存在连接的权限。 修改完成后， 只有再新建的连接才会使用新的权限设置。连接完成后， 如果你没有后续的动作， 这个连接就处于空闲状态， 你可以在show processlist命令中看到它。 文本中这个图是show processlist的结果， 其中的Command列显示为“Sleep”的这一行， 就表示现在系统里面有一个空闲连接。

- **长连接与短连接** 
  - 长连接指连接成功后，如果客户端有请求，则一直使用同一个连接
  - 短连接指执行很少的几次查询之后，就断开连接。
  - 长连接mysql的，如果太久没有动静，mysql默认8h会自动断开，可以使用wait_timeout参数控制。
-  **全部使用长连接Mysql内存涨特别快的解决方案** 
  - 定期断开长连接。或者执行一个占用内存大的查询之后断开连接，之后再重连。
  - 5.7以上版本可以通过执行mysql_reset_connection来重新初始化连接资源。 这个过程不需要重连和重新做权限验证，但是会将连接恢复到刚刚创建完时的状态

## 查询缓存

- 连接建立完成之后，会到查询缓存中查询数据。查询缓存的存储默认key为查询语句，而value为结果。
- **查询缓存弊大于利，因为只要有表更新，这个表相关的缓存就会被清除。**
- query_cache_type 设置成DEMAND，可取消查询缓存。
- 显示的查询缓存数据 `mysql> select SQL_CACHE * from T where ID=10；`
- mysql 8 版本直接移除了查询缓存。

1. ## 优化器

```SQL
-- 查看优化器生成的执行计划
EXPLAIN SELECT id, name FROM user WHERE age > 18;

-- 8.0+ 可查看优化器追踪信息（调试用）
SET optimizer_trace="enabled=on";
SELECT ...;
SELECT * FROM information_schema.OPTIMIZER_TRACE;
```

在开始执行之前， 还要先经过优化器的处理。

- **优化器是在表里面有多个索引的时候，决定使用哪个索引**；或者在一个语句有多表关联（join）的时候， **决定各个表的连接顺序**。比如你执行下面这样的语句，这个语句是执行两个表的join： `mysql> select * from t1 join t2 using(ID) where t1.c=10 and t2.d=20;`
- 既可以先从表t1里面取出c=10的记录的ID值，再根据ID值关联到表t2，再判断t2里面d的值是否等于20。
- 也可以先从表t2里面取出d=20的记录的ID值，再根据ID值关联到t1，再判断t1里面c的值是否 等于10。 这两种执行方法的逻辑结果是一样的，但是执行的效率会有不同，**而优化器的作用就是决定选择效率高的方案。**

🔍 优化器核心工作：

1. 基于成本的优化（CBO）：估算不同执行路径的"成本"（IO+CPU+网络），选最小值
2. 索引选择：单索引？联合索引？索引合并？全表扫描？
3. Join顺序：驱动表选择（小表驱动大表）、Join算法（NLJ/BNL/Hash Join）
4. 子查询改写：IN/EXISTS转Join，派生表物化

```SQL
-- 案例：优化器选错索引怎么办？
-- 原SQL（走age_idx，但回表率高）
EXPLAIN SELECT * FROM user WHERE age > 18 AND status = 1;

-- 方案1：强制索引（临时）
SELECT * FROM user FORCE INDEX(status_idx) WHERE age > 18 AND status = 1;

-- 方案2：创建覆盖索引（根本）
ALTER TABLE user ADD INDEX idx_age_status (age, status, id, name);

-- 方案3：更新统计信息（优化器"失智"常因统计信息过期）
ANALYZE TABLE user;
```

1. ## 执行器

```Plain
mysql> select * from T where ID=10;
```

-  首先判断语句是否与查询权限，若无则直接返回 
-  比如我们这个例子中的表T中，ID字段**没有索引，那么执行器的执行流程是这样的：** 1.调用InnoDB引擎接口取这个表的第一行，判断ID值是不是10，如果不是则跳过，如果是则将这行存在结果集中； 2.调用引擎接口取“下一行”，重复相同的判断逻辑，直到取到这个表的最后一行。 3.执行器将上述遍历过程中所有满足条件的行组成的记录集作为结果集返回给客户端。 

**对于有索引的表，执行的逻辑也差不多。**

1. 第一次调用的是“取满足条件的第一行”这个接口，之后循环取“满足条件的下一行”这个接口，这些接口都是引擎中已经定义好的。
2. 你会在数据库的慢查询日志中看到一个rows_examined的字段，表示这个语句执行过程中扫描了多少行。这个值就是在执行器每次调用引擎获取数据行的时候累加的。

在有些场景下，执行器调用一次，在引擎内部则扫描了多行，因此引擎扫描行数跟rows_examined并不是完全相同的。

1. # 一条SQL查询和更新过程

1. ## 一条查询sql执行过程

1. 客户端发起请求，进入连接器，连接器就是管理链接，权限验证，看看你的这个账号密码对不对，如果通过，进入下一步
2. 此时有两个分叉 
   1. **先会查询缓存，缓存如果有结果，直接返回结果，如果没有，进行分析器步骤**
   2. 走分析器，进行词法分析，语法分析，比如select from where 这几类关键字，然后到优化器，看看能不能进行优化性能之类，比如索引下推等，最后到执行器，开始执行，返回结果
   3. **注意：查询缓存的失效非常频繁，只要有对一个表的更新，这个表上所有的查询缓存都会被清空。因此很可能你费劲地把结果存起来，还没使用呢，就被一个更新全清空了。对于更新压力大的数据库来说，查询缓存的命中率会非常低。除非你的业务就是有一张静态表，很长时间才会更新一次。比如，一个系统配置表，那这张表上的查询才适合使用查询缓存。**
3. 默认是用的innodb引擎

```SQL
SELECT name, age FROM users WHERE id = 100;

① 客户端发送 SQL
    │
    ▼
② 连接器：建立/复用连接，身份验证，读取权限到内存
    │
    ▼
③ ~~查询缓存~~（MySQL 8.0 已移除，跳过）
    │
    ▼
④ 分析器：
    ├─ 词法分析：拆成 SELECT / name / age / FROM / users / WHERE / id / = / 100
    ├─ 语法分析：检查语法正确性 → 生成 AST
    └─ 语义分析：users 表存在？name/age/id 列存在？有 SELECT 权限？
    │
    ▼
⑤ 优化器：
    ├─ 发现 id 是主键
    ├─ 决定使用主键索引进行查找
    └─ 生成执行计划：主键等值查询（const/ref 级别）
    │
    ▼
⑥ 执行器：
    ├─ 最终权限校验
    ├─ 调用 InnoDB 的 handler 接口
    │   handler::index_read(PRIMARY, key=100)
    │   → InnoDB 从主键 B+ 树中找到 id=100 的记录
    │   → 返回完整行数据
    ├─ 取出 name 和 age 字段
    └─ 返回结果给客户端
    │
    ▼
⑦ 客户端接收结果集
```

1. ## 一条更新sql执行过程

![img](https://my.feishu.cn/space/api/box/stream/download/asynccode/?code=MjIyZTMxNTI2MWQxMTA0MmY1ODdjY2FhZmJiZWRmM2ZfTk9Yd3VCMUg4Rnd3bGsxblBrSWlBcmtsaHFMRDBFcG5fVG9rZW46UzVjR2JxTkZWb2E4MGJ4YVduMWNGN0RhblNlXzE3NzgzOTQ4MzA6MTc3ODM5ODQzMF9WNA)

```SQL
update `article` set `commentcnt` = `commentcnt` + 1 where `id` = 2;
```

1. **连接器会先检查权限**，若没有权限就直接返回错误信息
   1. 如果有权限就会**清除查询缓存**（MySQL 8.0版本之前）
   2. **将article表所有缓存结果都清空**（一般不建议使用查询缓存）。接下来执行下一步。
2. 通过分析器先进行**词法分析**，**提取sql语句里面的关键字**。
   1. 示例SQL取的update，然后提取要更新的表名article ，更新条件是id= 2 
   2. 然后进行语法分析，**判断sql语句是否正确**，如果有错会返回报错信息，否则执行下一步。
3. 优化器**确定执行方案**。
   1. 优化器根据自己的优化算法选择一个执行效率最好的一个方案。
   2. 比如：优化器会去找id字段有没有索引，使用id主键索引，执行计划确定后就会执行下一步。
4. 执行器首先会判断当前用户对article表是否有更新的权限
   1. 如果没有权限就会返回权限错误
   2. 若有权限会打开表执行，根据表的引擎定义调用引擎提供的接口，返回引擎执行结果。

**作者的解释：**

- 执行器先找引擎取 ID=2 这一行。
  - ID 是主键，引擎直接用树搜索找到这一行。
  - 如果ID=2 这一行所在的数据页本来就在内存中，就直接返回给执行器；
  - 否则，需要先从磁盘读入内存，然后再返回。
- 执行器拿到引擎给的行数据，把这个值加上 1
  - 比如原来是 N，现在就是 N+1
  - 得到新的一行数据，再调用引擎接口写入这行新数据。
- 引擎将这行新数据更新到内存中
  - 同时将这个更新操作记录到 redo log 里面
  - 此时redo log 处于 prepare 状态。然后告知执行器执行完成了，随时可以提交事务。
- 执行器生成这个操作的 binlog，并把 binlog 写入磁盘。
- 执行器调用引擎的提交事务接口，引擎把刚刚写入的 redo log 改成提交（commit）状态，更新完成

1. # 插件式存储引擎设计

1. ## 设计思想

### 为什么是插件式架构？

```Plain
传统数据库（如早期 Oracle/SQL Server）：
  SQL 解析 + 优化 + 存储 → 全部耦合在一起
  想换存储方式？得改整个数据库内核

MySQL 的做法：
  Server 层负责 SQL 解析和优化（统一标准）
  引擎层负责数据存储和检索（可插拔）
  通过 Handler API 桥接

好处：
  1. 同一个 MySQL 实例中，不同表可以使用不同引擎
  2. 可以按业务场景选择最合适的引擎
  3. 引擎可以独立升级，不影响 Server 层
  4. 社区可以开发第三方引擎（RocksDB、TokuDB、ColumnStore）
```

### 查看与设置引擎

```SQL
-- 查看所有支持的引擎
SHOW ENGINES;

-- 创建表时指定引擎
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
) ENGINE=InnoDB;

-- 修改已有表的引擎
ALTER TABLE users ENGINE=InnoDB;
```

1. ## InnoDB 引擎详解

### 核心定位

**MySQL 5.5 之后的默认引擎**，面向 **OLTP（在线事务处理）** 场景。

### 核心特性

```Plain
✅ 事务支持（ACID 完整实现）
✅ 行级锁（并发性能好）
✅ 外键约束
✅ 崩溃恢复（redo log + undo log）
✅ MVCC（多版本并发控制）
✅ 聚簇索引（数据和主键索引存储在一起）
✅ 支持热备份
```

### 数据存储结构

```Plain
InnoDB 的表空间结构（从大到小）：

Tablespace（表空间）
├─ System Tablespace（ibdata1）—— 系统数据、undo log
├─ File-Per-Table Tablespace（.ibd）—— 每张表独立文件
├─ Undo Tablespace（独立 undo 表空间，MySQL 8.0）
└─ Temporary Tablespace —— 临时表

表空间内部：
Segment（段）
├─ 数据段（Leaf Node Segment）—— B+ 树的叶子节点
└─ 索引段（Non-Leaf Node Segment）—— B+ 树的非叶子节点

Extent（区）—— 1MB = 64 × 16KB 页
Page（页）—— 16KB，默认的基本 IO 单位
Row（行）—— 实际数据
```

### 聚簇索引 vs 二级索引

```Plain
聚簇索引（Primary Key）：
  ┌──────────────────────────────────────┐
  │  B+ 树叶子节点存储的是 完整行数据       │
  │  数据按主键顺序物理排列                 │
  │  一张表只有一个聚簇索引                 │
  └──────────────────────────────────────┘

二级索引（Secondary Index）：
  ┌──────────────────────────────────────┐
  │  B+ 树叶子节点存储的是 主键值           │
  │  查到主键值后，需要回表到聚簇索引取数据   │
  │  一张表可以有多个二级索引               │
  └──────────────────────────────────────┘
```

### Buffer Pool（缓冲池）

```Plain
InnoDB 的核心缓存组件，数据页和索引页都在这里缓存：

Buffer Pool（默认 128MB，生产环境通常设为物理内存的 50%-75%）
├─ 数据页（Data Page）—— 表数据
├─ 索引页（Index Page）—— 索引数据
├─ undo 页 —— 回滚数据
├─ Change Buffer —— 二级索引的写缓冲
├─ 自适应哈希索引（AHI）
└─ 插入缓冲（Insert Buffer）

读取数据时：
  Buffer Pool 中有 → 直接返回（内存读）
  Buffer Pool 中没有 → 从磁盘读取 → 放入 Buffer Pool → 返回

修改数据时：
  先修改 Buffer Pool 中的页（标记为脏页）
  后台线程异步将脏页刷到磁盘（Checkpoint 机制）
```

1. ## MyISAM 引擎详解

### 核心定位

### 核心定位

**MySQL 5.5 之前的默认引擎**，面向 **OLAP（在线分析处理）** 场景。

### 核心特性

```Plain
❌ 不支持事务
❌ 不支持行级锁（只支持表级锁）
❌ 不支持外键
❌ 不支持崩溃恢复
❌ 不支持 MVCC
✅ 全文索引（MySQL 5.6 之前，InnoDB 不支持全文索引时是 MyISAM 的优势）
✅ 表级锁简单高效（读多写少场景性能好）
✅ 数据文件和索引文件分离
✅ 压缩表（只读压缩表节省空间）
```

### 数据存储结构

```Plain
每张 MyISAM 表有三个文件：
├─ table_name.frm  —— 表结构定义
├─ table_name.MYD  —— 数据文件（MYData）
└─ table_name.MYI  —— 索引文件（MYIndex）

数据存储方式：
  非聚簇索引 —— 索引和数据是分开存储的
  索引的叶子节点存储的是数据记录的物理地址（指针）

查询流程：
  通过 MYI 文件找到索引 → 获取数据行的物理地址
  → 到 MYD 文件中根据地址读取数据
```

### 锁机制

```Plain
MyISAM 只有表级锁：

读锁（共享锁 / Read Lock）：
  lock table users read;
  → 其他线程可以读，不能写

写锁（排他锁 / Write Lock）：
  lock table users write;
  → 其他线程不能读也不能写

问题：
  SELECT 会自动加读锁，UPDATE/DELETE 会自动加写锁
  一行写操作会锁住整张表 → 并发性能极差
```

1. ## Memory 引擎

### 核心特性

```Plain
✅ 数据全部存在内存中
✅ 速度极快（纯内存操作）
✅ 默认使用哈希索引
❌ 重启数据丢失（不持久化）
❌ 只支持表级锁
❌ 不支持 TEXT/BLOB 类型
⚠️ 使用固定长度存储（VARCHAR → CHAR），可能浪费内存
```

### 使用场景

```Plain
├─ 临时表（MySQL 内部临时表默认用 Memory 引擎）
├─ 缓存中间结果
├─ Session 级别的临时数据
└─ 数据量小、重启可丢弃的配置表
```

### 与 Redis 的区别

| 特性     | Memory 引擎   | Redis                         |
| -------- | ------------- | ----------------------------- |
| 数据结构 | 关系型表      | KV / List / Set / ZSet / Hash |
| 查询能力 | 支持 SQL      | 只有简单命令                  |
| 持久化   | ❌             | ✅ RDB / AOF                   |
| 分布式   | ❌ 单机        | ✅ Cluster                     |
| 使用方式 | 通过 SQL 访问 | 通过客户端 API                |

### 选择建议

```Plain
  ├─ 需要全文索引（MySQL 5.6 之前）
  └─ 数据压缩归档

  └─ 临时表、会话缓存、中间结果集
```

1. # 面试高频问题深度解析

1. ## 为什么 MySQL 不用 Redis 做缓存层？

这个问题的本质是：**MySQL 8.0 移除了查询缓存，那为什么不直接集成 Redis？**

### 答案：分层架构已经把这个问题解决了

```Plain
当前的业界标准架构：

客户端 ──→ 应用层（Java/Spring Boot）──→ Redis（缓存层）──→ MySQL（存储层）
                   │
                   └── 应用层负责缓存逻辑
                       ├─ Cache Aside Pattern（旁路缓存）
                       ├─ 先查缓存 → 缓存有则返回
                       ├─ 缓存没有 → 查 MySQL → 写回缓存
                       └─ 更新时先更数据库 → 再删缓存
```

### 具体原因分析

```Plain
原因 1：职责分离原则
  MySQL 的定位是「关系型数据库」，负责数据持久化和事务
  Redis 的定位是「高性能 KV 缓存」，负责热点数据加速
  两者职责不同，不应该在 MySQL 内部集成

原因 2：缓存策略需要业务定制
  ├─ 缓存什么？哪些字段？什么粒度？
  ├─ 缓存多久？TTL 怎么设？
  ├─ 缓存更新策略？Cache-Aside / Read-Through / Write-Through？
  ├─ 缓存穿透/击穿/雪崩怎么处理？
  └─ 这些都是业务层面的决策，不应该由数据库决定

原因 3：MySQL 之前的查询缓存已经证明了「内置缓存」的失败
  └─ 全局锁 + 粗粒度失效 → 性能瓶颈
  └─ 说明缓存需求太个性化，不适合做在数据库层

原因 4：网络开销问题
  MySQL 和 Redis 集成 → 每次查询多一次 Redis 访问
  而在应用层做缓存 → 可以直接在本地内存缓存（Caffeine）
  └─ 应用层可以做多级缓存（L1: 本地缓存, L2: Redis）
  └─ 比数据库层直接集成更灵活

原因 5：水平扩展能力
  Redis 集群 → 应用层可以自由配置分片策略
  如果 MySQL 内置 → 扩展方案受 MySQL 限制
```

### 面试回答模板

> "MySQL 和 Redis 的定位不同，MySQL 是关系型数据库负责持久化和事务，Redis 是高性能缓存负责热点加速。MySQL 之前的查询缓存已经证明内置缓存在通用场景下收益不大。缓存策略需要根据业务场景定制（TTL、更新策略、穿透处理），这些不适合固化在数据库层。实际架构中，应用层通过 Cache Aside 模式来协调 MySQL 和 Redis，这样既能利用 Redis 的高性能，又保持了职责分离和灵活性。"

1. ## MyISAM 为什么被淘汰？

### 核心原因

```Plain
原因 1：不支持事务
  现代业务几乎 100% 需要事务保证
  转账、订单、库存等操作没有事务 = 数据不一致的风险
  InnoDB 的 ACID 事务是刚需

原因 2：表级锁 = 并发灾难
  MyISAM：写一行数据 → 锁整张表
  InnoDB：写一行数据 → 只锁这一行
  
  举例：
  用户表有 100 万行数据
  MyISAM：更新 user_id=1 的名字 → 整张表锁住 → 其他 999,999 行也不能读写
  InnoDB：更新 user_id=1 的名字 → 只锁 user_id=1 这一行 → 其他行不受影响

原因 3：没有崩溃恢复能力
  MyISAM：MySQL 崩溃后，表可能损坏 → 需要 REPAIR TABLE
  InnoDB：通过 redo log 实现崩溃恢复 → 数据不丢

原因 4：没有 MVCC
  MyISAM 的读操作会阻塞写操作
  InnoDB 的 MVCC 实现了读写不阻塞（快照读）

原因 5：InnoDB 在 MySQL 5.6 之后补齐了短板
  MySQL 5.6：InnoDB 支持全文索引
  MySQL 5.7：InnoDB 性能大幅提升
  MySQL 8.0：默认引擎 = InnoDB，MyISAM 的最后优势消失
```

### MyISAM 残存的一点优势

```Plain
优势 1：表级锁在「全表扫描 + 批量更新」场景下反而更快
       因为不用逐行加锁，锁开销小

优势 2：压缩表（只读场景）
       MyISAM 支持 myisampack 压缩，节省 50%-80% 空间
       适合归档数据、只读日志

优势 3：count(*) 快
       MyISAM 维护了一个行数计数器，直接返回
       InnoDB 需要扫描（因为 MVCC，每个事务看到的行数可能不同）

但在这些场景下，也有更好的替代方案：
  压缩归档 → Archive 引擎 / 分区表
  全文索引 → InnoDB 已支持
  count(*) → 用 Redis 计数器 / 单独汇总表
```

### 面试回答模板

> "MyISAM 被淘汰的核心原因是不支持事务和行级锁。现代业务几乎都需要事务保证，而 MyISAM 的表级锁在高并发场景下是致命短板——一行写操作锁整张表。另外它没有崩溃恢复能力，MySQL 崩溃后数据可能损坏。InnoDB 在 MySQL 5.6 之后补齐了全文索引的短板，MyISAM 的最后优势也消失了。现在除了极少数只读压缩归档场景，新表都应该用 InnoDB。"

## 5.3 其他高频面试题

### Q1：一条 SQL 的执行流程是什么？

> 连接器（认证+权限） → ~~查询缓存~~（8.0移除）→ 分析器（词法+语法+语义）→ 优化器（选择执行计划）→ 执行器（调用引擎 API）→ 返回结果

### Q2：为什么 InnoDB 要用 B+ 树而不是 B 树或哈希？

> - B+ 树的叶子节点存储完整数据并用链表相连 → 支持范围查询和顺序遍历
> - B 树的非叶子节点也存数据 → 树高度更高 → IO 次数更多
> - 哈希不支持范围查询（WHERE age > 18 无法使用）
> - B+ 树高度通常 3-4 层 → 2-4 次 IO 就能找到数据

### Q3：InnoDB 和 MyISAM 都有 B+ 树索引，区别是什么？

> - InnoDB：**聚簇索引**，叶子节点存储完整行数据
> - MyISAM：**非聚簇索引**，叶子节点存储数据行的物理地址
> - 所以 InnoDB 的主键查询更快（找到索引就找到了数据），MyISAM 还需要多一步到数据文件取数据

### Q4：MySQL 的 Server 层和引擎层各负责什么？

> - Server 层负责 SQL 解析、优化、执行协调，以及 binlog、内置函数等
> - 引擎层负责数据的物理存储、索引实现、事务实现、锁机制等
> - 两者通过 Handler API 交互，实现了逻辑和存储的解耦

### Q5：既然 InnoDB 引擎有了 redo log，为什么还要 binlog？

> - **redo log**：InnoDB 特有，物理日志，记录"某个数据页做了什么修改"，用于崩溃恢复
> - **binlog**：Server 层，逻辑日志，记录"SQL 语句的原始逻辑"，用于主从复制和数据恢复
> - 两者配合使用，通过 **两阶段提交（2PC）** 保证数据一致性
